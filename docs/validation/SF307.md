# SF-307 optional Walrus runtime: parse safety and explicit limits

Recorded by Claude (claude-opus-5-5) on 2026-11-24 on branch
`work/suifleet/sf-307-0eebd125`. These are local OpenEmbedded parse/task
results on the WSL host, not hardware, image-boot or publication evidence.

## Change

- `suifleet-walrus-codec` has a parse-time guard. If the local fetcher
  cannot find any `file://` codec input, the recipe is skipped and the reason
  names the missing files. It no longer stops parsing for every target.
  An explicit request for the codec fails with that reason. Remote inputs are
  left to the fetcher's `sha256sum` and `do_verify_codec`.
- The codec and `suifleet-node` are skipped, with a reason, on any target
  other than little-endian AArch64 (`HOST_ARCH = "aarch64"`) with
  `TCLIBC = "glibc"`; big-endian `aarch64_be` is refused. `COMPATIBLE_HOST` alone also
  accepts `aarch64-*-linux-musl`. There is no fallback to another libc,
  architecture or source.
- This change does not touch any pin line. Per the boundary in
  [#820](https://github.com/tyler-suifleet/suifleet/issues/820), SF-295 owns
  the public pins and their publication. SF-295 merged them in PR #841
  (main `75202975`). The SF-307 branch merged that main, so the committed
  default codec `SRC_URI` is now SF-295's public, checksum-pinned archive. The
  `file://` guard still covers a downstream bbappend that points the codec at
  absent local files.

## Cached missing-input skip repair (2026-11-26)

Run by Claude (claude-opus-5-5) in response to integration review 5013 on
PR #1093. Finding: the guard skipped the codec without recording which files
would make it eligible. BitBake keeps only `__depends` (file mtimes) for a
skipped recipe in its parse cache, so after a downstream `file://` override was
parsed with the inputs absent, staging the files left the recipe skipped until
metadata or the cache changed.

Repair: the guard now calls `bb.utils.which(FILESPATH, name, history=True)` and
passes every searched candidate, absent ones included (mtime 0), to
`bb.parse.mark_dependency`. When a candidate appears, its mtime no longer
matches and BitBake reparses the recipe. Kirkstone, Scarthgap and Wrynose
BitBake all record `file_depends` before the skipped-recipe early return in
`lib/bb/cache.py`.

`scripts/tests/test_yocto_codec_bitbake_cache.py` runs the committed recipe in a
minimal standalone BitBake project (no OE-Core) with a bbappend pointing it at
five local inputs. It runs `bitbake -e suifleet-walrus-codec` with the inputs
absent and checks the skip reason and the on-disk `bb_cache.dat`. It then
stages the files without changing any metadata file and without touching or
removing the cache, and requests the recipe again. A control test applies the
pre-repair guard text to show the harness really uses the cache. Results with
`SUIFLEET_BITBAKE_DIRS` set to the three kas-pinned BitBake trees:

| BitBake | Repaired recipe after staging | Pre-repair guard (control) |

| 2.0.0 (Kirkstone poky `445a6223`) | resolves: rc 0, `PN` and local `SRC_URI` printed | stays skipped: "optional Walrus codec inputs not found" |
| 2.8.1 (Scarthgap poky `a53cae3d`) | the same; the log shows "1 parsed, 0 cached" | the same |
| 2.18.0 (Wrynose bitbake `51fd94a`) | the same | the same |

`test_yocto_runtime_packaging.py` also has a new offline test that checks every
searched candidate is a parse dependency. It fails against the previous recipe.
Without `SUIFLEET_BITBAKE_DIRS`, the BitBake test is skipped. Hosted CI has no

## Fetcher-equivalent input resolution repair (2026-11-26)

Run by Claude (claude-opus-5-5) in response to integration review 5020 on
candidate PR #1095. Finding: the guard looked up the raw URI text in
`FILESPATH` only. BitBake's local fetcher decodes URI escapes, takes absolute
paths as is and, on BitBake 2.0, falls back to `DL_DIR` for a relative input.
The guard therefore skipped a supported recipe whose inputs were present, for
example a percent-encoded absolute `file://` URI (all three releases) or
inputs staged only in `DL_DIR` (Kirkstone).

Repair: the guard builds `bb.fetch2.Fetch(local, d, cache=False,
localonly=True)` for the `file://` entries, as `get_checksum_file_list` does,
and asks the local method for its candidates (`localfile_searchpaths`, or
`localpaths` on BitBake 2.0). Every candidate is still a parse dependency. An
input is missing only when the fetcher's chosen path (the last candidate) does
not exist. Scarthgap and Wrynose removed the `DL_DIR` fallback, so a
`DL_DIR`-only input is genuinely absent to their fetcher and the skip stands
there; the guard does not add a fallback that the fetcher lacks.

New real-BitBake tests in `scripts/tests/test_yocto_codec_bitbake_cache.py`
(the harness now sets `DL_DIR`):

| Test | 2.0.0 (Kirkstone `445a622`) | 2.8.1 (Scarthgap `a53cae3`) | 2.18.0 (Wrynose `51fd94a`) |
| --- | --- | --- | --- |
| present percent-encoded absolute inputs (`abs%20dir`) | kept, rc 0 | kept | kept |
| absent percent-encoded absolute inputs | skipped, names the URI as written | the same | the same |
| cached skip, then encoded absolute inputs staged | kept after staging | the same | the same |
| inputs only in `DL_DIR` | kept | skipped (no fetcher fallback) | skipped |
| cached skip, then `DL_DIR` inputs staged | kept after staging | not applicable | not applicable |
| control: earlier raw-text guard with present inputs | skipped (encoded and `DL_DIR`) | skipped (encoded) | skipped (encoded) |
| existing cached-skip test and unrecorded control | pass | pass | pass |

## Big-endian AArch64 repair (combined review #5044)

The integration review of candidate PR #1097 found that `suifleet-node` used
`COMPATIBLE_HOST = "aarch64.*-linux"`. BitBake applies `re.match` to `HOST_SYS`,
and Scarthgap's `aarch64_be` tune gives `aarch64_be-poky-linux`, so a big-endian
target could fetch and package the little-endian Node.js executable. The recipe
now uses `COMPATIBLE_HOST = "aarch64-.*-linux"` and its parse guard also
requires `HOST_ARCH = "aarch64"`, like the codec. The skip reason names the
rejected `HOST_SYS`.

`test_node_is_little_endian_aarch64_only` checks that the committed pattern
matches `aarch64-poky-linux` (glibc, and musl for the libc guard) and rejects
`aarch64_be-poky-linux`, x86-64, 32-bit Arm and RISC-V. It also checks that both
the Node and codec guards skip `aarch64_be`. With the earlier pattern restored
on a scratch copy, that test fails.
