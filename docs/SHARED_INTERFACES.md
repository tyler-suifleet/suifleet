# Shared fleet interfaces

SF-005 defines the protocol in [fleet-v1.json](../interfaces/fleet-v1.json) and the recipe wire format in [recipe.schema.json](../interfaces/recipe.schema.json). The fleet catalog records public/entry calls, complete parameter and return types, reference mutability, struct abilities, ordered fields, required type origins, protocol/schema versions and status codes. It covers the five project modules; Sui framework objects such as `UpgradeCap` remain SDK/deployment-manifest responsibilities.

`scripts/generate_interfaces.py` produces:

- TypeScript SDK call encoders and BCS layouts in `dapp/src/lib/fleet-protocol.ts`; frontend transaction builders use these encoders.
- Lightweight version/status/type-origin constants in `dapp/src/lib/protocol-version.ts`; frontend manifest validation and labels use these constants.
- A recipe type and runtime validator in `dapp/src/lib/recipe-schema.ts`; upload rejects malformed/unknown-version recipes before storing bytes.
- Rust Serde wire structs, event/recipe definitions, typed JSON call-argument encoders and constants in `suifleet-edge/src/protocol.rs`. Address/ID/UID fields in BCS structs are fixed 32-byte arrays; the legacy JSON event view uses strings. The daemon uses the generated event, recipe, call encoders/type names and version/status constants.
- A Move test comparing actual compiled status getters to the shared status values.

Device telemetry (SF-019) is off-chain and not part of this ABI catalog. Its snapshot format, signature and status rules are in [TELEMETRY.md](TELEMETRY.md). [telemetry-cases.json](../interfaces/telemetry-cases.json) holds a vector signed with Mysten's TypeScript SDK and the shared status cases. The daemon reproduces the vector byte for byte, and the indexer and the dApp both verify it and evaluate the cases.

Generated files have no timestamps and must not be edited manually. The Python deployment-manifest resolver reads the same catalog. Both clients now require the same type-origin set, including authoritative receipts and the signer-bound report event. Existing manifests generated by the resolver already include these types; a handwritten incomplete manifest must be regenerated.

`interfaces/compat/` holds the SF-028 [Greengrass compatibility](GREENGRASS_COMPATIBILITY.md) matrix and proposed adapter fixtures. They are not generated and are not a current wire contract: only the AWS-recipe cases are run against the current native validators, which reject AWS recipes and accept the expected native translations. `make test-compat` checks them.

## Normal development and CI

```bash
make generate-interfaces   # regenerate clients only if compiled ABI matches the reviewed catalog
make check-interfaces      # compile Move, compare ABI/layouts and generated files, run negative/vector cases
make ci                    # also Move/Rust, OTA/restart/component, manifest/wallet, typecheck/build
```

The checker uses actual `sui move summary` compiler output, rather than matching field names in Move source. It compares complete callable signatures and ordered struct fields, including compiler-generated `dummy_field: bool` for empty dynamic-field keys. The older name/arity scanner remains an additional guard for references outside the generated helpers.

Negative tests mutate real compiler summaries to change field types/order, key layouts, argument types/mutability, returns, abilities and callable visibility. CI fails on any drift or stale generated file. Independent fixed BCS bytes are encoded/decoded by the actual TypeScript SDK and Rust `bcs` test serializer. Both clients consume the same positive/negative recipe cases. The daemon uses its existing runtime BCS dependency for generated wire vectors.

For real generated calls against the pinned 1.81.1 localnet, without public-network access or user wallets:

```bash
docker run --rm --network none --user "$(id -u):$(id -g)" \
  -e INSIDE_DEV_CONTAINER=1 -v "$PWD":/workspace \
  -v sui_move-cache:/home/dev/.move -w /workspace suifleet-dev:sf004 \
  make test-protocol-live
```

Install locked frontend dependencies first. This test creates temporary keys/state and compiles a temporary copy of the contracts, publishes only on the disposable loopback network, then exercises enrollment, groups, verified deployment, authoritative reporting and cleanup through the generated encoders. It checks execution effects. The compiler uses the implicit testnet build environment with RPC tree shaking disabled; transaction execution targets the owned local chain. Its explicit empty keystore prevents compiler key generation, and CLI output is suppressed. The runner rejects an existing service or any container network beyond loopback. This exercises the generated interfaces through the supported gRPC client on an isolated chain. Public networks, browser-extension wallets, Walrus and physical Pi acceptance remain separate.

## Deliberate changes and compatibility

1. Agree on the interface in the owning ticket before concurrent clients change. Preserve public signatures, layouts and abilities for compatible upgrades.
2. Edit the contracts and reviewed catalog metadata/recipe schema. To capture an intentional compiled ABI change, run `python3 scripts/generate_interfaces.py --capture`; this preserves version/status/required-origin metadata and explicitly updates the ABI snapshot. Review that diff rather than accepting a failing check automatically.
3. Regenerate both clients, run the checks above and the relevant live upgrade/mixed-client acceptance. Update deployment manifests/client version ranges together. Never run `--capture` in CI or to silence unexplained drift.

Catalog format version, manifest schema, fleet protocol, deployment object schema, recipe version and receipt authority generation have different meanings. The current supported fleet protocol and manifest schema are 1; recipe wire versions are `1.0`, `1.1`, which adds `componentDependencies` ([COMPONENT_DEPENDENCIES.md](COMPONENT_DEPENDENCIES.md)), `1.2`, which adds component configuration and `lifecycle.validate` ([OPERATIONS.md](OPERATIONS.md#component-configuration-sf-015)), and `1.3`, which adds [deployment service configuration](DEPLOYMENT_SERVICES.md). The optional catalog origin group and supported deployment schemas `[1,2,3]` are documented in [COMPONENT_CATALOG.md](COMPONENT_CATALOG.md). Schema 3 adds [staged rollout grants and durable coordinator state](STAGED_ROLLOUTS.md). Unknown manifest protocols fail during configuration validation; unknown deployment schemas and recipe versions fail before apply. `Receipts.version` is an authority generation; it is not the recipe or fleet protocol version.

An additive layout/API change still needs explicit client/catalog review and per-type introduction origins. A breaking layout is not made safe by changing a version number. Package upgrades do not rerun initializers, migrate objects or disable old entry points; authoritative-state migration and old-package bypass tests remain required.

Both clients apply the same recipe rules: the frontend before upload, the daemon before apply. Configuration fields and `lifecycle.validate` require schema `1.2` and an install or run command; pointers follow RFC 6901; `defaults`/`merge` are bounded to 4096 values and depth 32 (`CONFIGURATION_LIMITS`); and no value may sit at or above a confidential pointer, since recipes are public. Optional fields that the schema does not declare nullable must be absent rather than null, and `lifecycle`/`configuration` must be JSON objects. `interfaces/recipe-cases.json` holds the shared accept/reject cases. Authentication of recipe and artifact digests remains required.

Both clients consume the generated interfaces after integrating SF-003 and SF-004. The Rust transaction builder uses generated module/function names with typed object IDs and u8 statuses, and verifies the simulated transaction before signing. Obsolete JSON-RPC argument encoders were removed. Reference-returning Move helpers have no generated transaction encoders. The full ABI snapshot lives separately in `fleet-abi.ts` and is not imported into application bundles.

The additive SF-083 `fleet_budget` module is in the same reviewed ABI, with an
all-or-none optional origin group `fleet_budget`; manifests without it keep working
and the daemon's `[budget]` requires it. The separately published `fleet_storage`
package (Walrus dependency) is not in this catalog: its dApp calls are checked by
`check_contract_interfaces.py` against its own compiled summary. The separately published `fleet_data` package
is compiled and checked by the same gate, including archive types and both explicit
Seal approval calls; missing types/functions and wrong argument counts fail. The pinned Walrus
exchange calls are listed as reviewed external references. Storage purchases go through
`fleet_storage::refill_pool`, so the dApp calls no Walrus `System` function
directly. See [FLEET_BUDGET.md](FLEET_BUDGET.md).

The additive SF-089 handover API and `fleet_handover::Handover` BCS layout are in
the same reviewed ABI. Its optional origin group permits existing deployments
without handover to keep working. Manifest resolution records the new type's own
introduction package; the dApp verifies that origin before reading a handover.
Existing DeviceGroup/DeploymentRecord/DeviceOwnerCap origins and layouts remain
unchanged. See [fleet authority migration](FLEET_HANDOVER.md).

SF-138 adds the all-or-none optional `rollout_health` origin group for
`deployment_manager::RolloutHealthKey` and `RolloutHealth`. Historical manifests
and their recovery receipts remain valid without it. The new staged-rollout gate
requires an upgraded package and regenerated manifest containing the group; it
never falls back to HTTP or the legacy creator-attested gate.
